2. PROJECT SCOPE AND DOMAIN

Project name: ShiftSync.
Formal title: Duty Roster Management with Coverage Validation and Approved Shift Exchanges.
Setting: a fictional college computer-lab support team.

Build for one institution, two labs, approximately 12 fictional staff members, and one supervisor. There are exactly two application roles: staff and supervisor. The supervisor is not assigned lab duties in this version. A staff qualification such as technician is distinct from an application permission role.

Staff submit availability, view published duties, request two-way exchanges, respond to incoming requests, and track decisions. Supervisors build weekly rosters, identify staffing gaps, publish complete schedules, review swaps, and export reports.

The main workflow is:
Availability -> draft roster -> coverage checks -> publication -> swap request -> colleague acceptance -> supervisor approval -> atomic assignment exchange -> notifications and history.

Required differentiators:
- Coverage validation: sufficient headcount and at least the required number of technicians for every lab/time block.
- Explainable eligibility: show why a person or exchange is eligible or blocked.
- Approval preview: show both assignments and coverage before and after the proposed exchange.

Scope limits:
- Monday-Friday schedules; morning 09:00-12:00 and afternoon 13:00-16:00 in Asia/Kolkata by default.
- Manual assignments assisted by eligibility checks, not automatic roster optimization.
- Two-way swaps within the same published week only.
- In-app notifications, not email or SMS.
- No payroll, biometric/GPS attendance, one-way handovers, open-shift marketplace, overnight shifts, AI scheduling, payments, employee surveillance, or multi-organization accounts.
- No real-time attendance module. Reports show scheduled hours, not verified worked hours.

6. AVAILABILITY AND CANONICAL DATES

Availability is keyed by staff ID, local date, and morning/afternoon block. States are available, unavailable, and not_submitted. New cells default to not_submitted; unknown is never treated as available. Users can save a partially completed week, but only explicitly available blocks are eligible for assignment.

Provide labelled controls, select-all-for-day/week actions with confirmation when overwriting existing choices, a live available-block count, and clear saved/unsaved feedback. Ordinary PHP form submission must also work. Persist only allowed fields and validate dates, block IDs, and staff ownership in PHP.

Do not collect reasons for unavailability. Availability must never be changed retroactively for a started block.

If a proposed availability change would make an existing assignment unavailable or unknown, reject it with the conflicting assignment identified. The staff member must request a swap or contact the supervisor. This applies to draft and published assignments so planning never silently breaks. Other future availability cells remain editable; invalidate pending swaps that become ineligible during the same saved mutation.

Week keys are local Monday dates. Availability uses local date/block keys. Duty startsAt/endsAt are unambiguous UTC ISO timestamps generated by PHP from the configured timezone and block definition. Display all duty times explicitly in the institution timezone using proper formatting.

Avoid parsing a bare local SQL/date string with JavaScript and then calling toISOString(). Do not let the organizer's browser timezone change the intended duty time. Test date handling in Asia/Kolkata, UTC, and America/New_York. All cutoffs use server time, never a client-supplied clock.

7. DUTY SLOTS, ASSIGNMENTS, AND COVERAGE

A duty slot is one lab, one local date, and one morning/afternoon period. An assignment links exactly one staff member to a duty slot. Keep assignment IDs stable; a swap exchanges their staff IDs, not their times or locations.

Default requirements per slot: two people, including at least one qualified technician. Supervisors may configure small integer headcount/technician requirements while drafting; require 0 <= technicianMinimum <= headcount and headcount > 0. These are project staffing settings, not claims about legal staffing requirements.

Only active staff accounts may be assigned. All staff support general lab work; the technician qualification satisfies the specialized minimum. Count each assigned person once; a technician counts toward both overall headcount and the technician subset, not as two people.

Assignment checks:
- Explicit availability for the whole block.
- No duplicate assignment to that slot.
- No overlapping assignment in another location.
- No more people than the slot's requested headcount.
- Valid date and future start time.
- No assignment of the supervisor account.

Overlap rule: startA < endB AND endA > startB. Back-to-back intervals do not overlap. Evaluate across all retained draft/published assignments, excluding the exact assignments being exchanged in a hypothetical swap.

Drafts may be incomplete. Show missing people and missing technicians separately. Do not claim Fully covered merely because all headcount positions are filled.

A roster is a Monday-based week with status draft or published and a version. Create its two-lab/two-block weekday slots once; do not regenerate them on each request. Publishing requires every slot to meet its full requirements, all assignments to remain eligible, and all slots to start in the future. Draft versions prevent stale edits overwriting newer changes.

Keep the first version simple: after publication, block requirements, dates, locations, and assignments cannot be directly edited. Only approved swaps may exchange assignees. Explain this restriction in the UI and README. Do not add an incomplete republishing or emergency-override workflow. Past published rosters remain viewable for reports.

The staff roster shows only published weeks. The supervisor can inspect drafts. Staff hours reports count published assignments by default and clearly distinguish any draft planning totals.

8. SWAP STATE MACHINE AND ELIGIBILITY

Implement two-way swaps only, within the same published week, between two different active staff members and two distinct, non-overlapping future time blocks. Do not offer exchanges of identical time windows or exchanges with oneself.

States:
- awaiting_colleague
- awaiting_supervisor
- approved
- declined
- rejected
- withdrawn
- expired
- invalidated

Transitions:
- The owner of assignment A selects colleague B's assignment and submits a request: awaiting_colleague.
- Only B can accept to awaiting_supervisor or decline to declined.
- Only the requester can withdraw an awaiting request before final approval.
- Only the supervisor can approve or reject an accepted request. Rejection requires a short reason.
- Expired/invalidated/declined/rejected/withdrawn/approved records are terminal and remain in history.

Neither submission nor colleague acceptance changes the roster.

At most one nonterminal, nonexpired request may reference an assignment, whether incoming or outgoing. Enforce this inside the storage lock. Do not create hidden cross-request conflicts. The user can withdraw before selecting another exchange.

Candidate search and preview:
- List useful eligible candidates and a limited list of blocked candidates with reasons.
- Validate BOTH people in the post-swap state, not just the person receiving the first shift.
- Remove the two old allocations hypothetically, insert the exchanged staff, then validate availability, overlaps, duplicates, account activity, and requirements in BOTH affected duty slots.
- Recompute technician coverage: swapping a technician for a general assistant must not leave either slot short.
- Show assignments, location/time, qualification requirements, conflicts, and scheduled hours before/after. Fixed equal-duration blocks may leave weekly hours unchanged; say so instead of inventing improvements.

A request expires when server time reaches the earlier duty start. Derive expired status on reads and exclude expired records from pending counts/reservations. Persist expiration cleanup during relevant mutations; GET/poll requests must not silently rewrite the store. No cron job is required for correct eligibility.

Record the two original assignment owners and assignment versions in the request. Revalidate at submission, colleague acceptance, and final approval. If ownership/version has changed, the request is invalidated rather than applied to different assignments. Availability changes that invalidate an active request generate explanatory notices.

9. ATOMIC FINAL APPROVAL AND HISTORY

One approval must perform all of the following under one exclusive storage lock:
- Verify authenticated supervisor, CSRF, request ownership/state, and current request version.
- Confirm the colleague accepted and both duties are still future/published.
- Confirm original assignment owners and versions still match.
- Recompute the hypothetical exchanged roster and all eligibility/coverage checks.
- Exchange the staff IDs of both assignments and increment their versions and roster version.
- Mark the request approved with decision actor/time.
- Append one before/after audit entry and in-app notifications for the affected staff.
- Save the complete next state successfully before returning success.

If any check or write fails, neither assignment changes. Repeated approval of an already approved request returns its saved result without exchanging the staff again or duplicating notifications/history. Approval cannot be simulated through a status update that omits the actual roster changes.

For request creation, use a server-validated operation ID bound to the authenticated requester and payload. Exact retries return the existing request; mismatched reuse is a conflict. Validate first and only consume a new key when creation commits. Disable duplicate clicks as a UX aid, never as the sole protection.

Do not cache approval eligibility as truth. A visible green preview is advisory until PHP validates the current state at final commit. Give meaningful messages for stale requests, expired shifts, lost eligibility, and temporarily unavailable storage.

10. STORAGE, SECURITY, AND ERRORS

Use one private storage/state.json business snapshot containing schemaVersion, revision, counters, users, availability, rosters, dutySlots, assignments, swapRequests, notifications, auditLog, and bounded operation-ID mappings. User records may contain password hashes but must never be serialized wholesale to clients. Keep throttle bookkeeping separate so failed logins do not churn roster history.

All business readers/writers cooperate through one stable storage/state.lock file, distinct from the replaceable JSON file. Use shared locks for reads and an exclusive lock covering the complete read/validate/check/update/save operation. [R3]

Validate existing JSON and invariants. Unexpectedly missing or malformed state fails safely; never replace it silently with empty demo data. Write the complete next JSON to a same-directory temporary file, verify writes/flush/close, and replace the original only on successful supported replacement. On replacement failure preserve the original; do not delete it to force success. Release locks/handles in finally paths and provide a bounded timeout/retry response.

Document a single-server, persistent local-filesystem design; do not claim distributed scalability or database-grade crash durability. Provide explicit backup and restore CLI utilities. Seeding refuses to overwrite an existing store unless a clearly named reset option is intentionally used.

Security:
- Provision accounts through a CLI command; password_hash/password_verify; no reusable default production passwords.
- Session-based authentication, regeneration after login, strict/cookie-only sessions, HttpOnly and SameSite cookies, Secure on HTTPS.
- Server-enforced idle/absolute expiry and logout. Polls must not keep idle sessions alive.
- CSRF tokens for all state-changing actions including login/logout/availability, and no state-changing GET endpoints.
- Client can refresh a specifically rejected CSRF token and retry once only when that rejection guaranteed no mutation. Never blindly replay ambiguous network failures.
- Reject forged staff IDs, roles, qualifications, decision actors, statuses, timestamps, and claimed coverage totals.
- Appropriate server-side escaping; textContent for DOM text; ordinary escaped JSX. No user text through innerHTML/dangerouslySetInnerHTML.
- Bound input sizes; generic login failures and sensible session/IP throttles that do not block an entire classroom sharing an address.
- Never put passwords, tokens, session IDs, or private records into URLs, logs, public exports, or frontend bundles.
- Return sanitized per-role data and Cache-Control: no-store for authenticated responses.
- Release PHP session write locks promptly before longer storage operations; use a consistent lock order.

Suggested JSON response format:
Success: { ok: true, data: ..., meta: { revision, serverTime } }
Failure: { ok: false, error: { code, message, fields }, meta: { serverTime } }

Use appropriate HTTP statuses, such as 401 unauthenticated, 403 unauthorized/CSRF, 409 stale/conflicting state, 422 invalid fields, 429 throttled, and 503 storage unavailable. Missing authentication must not become a generic forever-loading UI.
