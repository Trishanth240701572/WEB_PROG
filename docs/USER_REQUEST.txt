============================================================

6. AVAILABILITY AND ROSTER RULES
============================================================

Use these availability states:
- available
- unavailable
- not_submitted

Unknown availability must not count as available.

A duty slot is one laboratory, one date, and one time block.

An assignment connects one staff member to a duty slot.

Default requirement:
Two people per duty slot, including at least one technician.

A technician counts as one person toward headcount and also satisfies
the technician requirement. Do not count them as two people.

Prevent:
- Assigning unavailable or unknown staff.
- Assigning the supervisor as a staff member.
- Duplicate assignments.
- Overlapping duties across laboratories.
- Overfilling a duty slot.
- Creating or modifying already started duties.

Overlap rule:
startA < endB AND endA > startB.

Back-to-back intervals are not overlapping.

Drafts may have gaps. Show missing headcount and missing technicians
separately.

Publishing requires:
- Complete headcount.
- Required technician coverage.
- Valid availability.
- No overlapping assignments.
- All duty start times still in the future.

Protect draft changes with version checks so an old browser tab
cannot overwrite newer edits.

For this version, a published roster is read-only except for approved
swaps. Do not add incomplete republishing or emergency override flows.

Reject an availability change that would invalidate an existing
assignment. Explain the conflict and direct the person to request a swap.

Changes to otherwise free future availability may invalidate a pending
exchange. Save a clear explanation and notification.

Store duty timestamps unambiguously in UTC, generated from the
institution timezone. Display them explicitly in Asia/Kolkata.

Do not let the browser's timezone alter the intended shift times.

============================================================
7. SHIFT-SWAP WORKFLOW
============================================================

A swap exchanges two assignments between two different staff members.

Both assignments must:
- Be in the same published week.
- Be in the future.
- Belong to the people participating.
- Have distinct, non-overlapping time windows.

Request states:
- awaiting_colleague
- awaiting_supervisor
- approved
- declined
- rejected
- withdrawn
- expired
- invalidated

Workflow:
1. Staff A selects their assignment and Staff B's proposed assignment.
2. PHP checks eligibility and creates awaiting_colleague.
3. Only B can accept or decline.
4. Acceptance changes the request to awaiting_supervisor.
5. Only the supervisor can approve or reject.
6. Only successful final approval changes assignment owners.

Neither requesting nor accepting changes the roster.

Allow at most one active pending request involving an assignment,
whether incoming or outgoing.

The requester may withdraw a pending request before approval.

A request expires when the earlier duty begins.

Preserve terminal requests in history.

8. EXPLAINABLE ELIGIBILITY AND APPROVAL
============================================================

Validate BOTH directions of every exchange.

Simulate removing the two original allocations and inserting the
proposed owners.

Check:
- Both staff accounts are active.
- Both are available for their incoming duties.
- Neither would overlap another assignment.
- Both affected slots retain required staffing and technician coverage.
- The original assignment owners and versions have not changed.
- The request is still pending and the duties have not started.

Show understandable reasons:
- Eligible.
- Unavailable for the incoming time block.
- Conflicts with another duty.
- Would leave Lab A without a required technician.
- Assignment already has a pending exchange.
- Shift has already started.

Before approval, show:
- Original assignments.
- Proposed assignments.
- Laboratory and time.
- Coverage before and after.
- Conflict checks.
- Scheduled hours before and after.

Equal-length shifts may leave weekly hours unchanged.
Display the real result rather than inventing an improvement.

At final approval PHP must recheck the latest saved state.

Under one storage transaction:
- Validate the request and permissions.
- Exchange both assignment owners.
- Update assignment/request versions.
- Mark the request approved.
- Save decision details.
- Append audit history.
- Add notifications.

If anything fails, neither assignment changes.

Approving the same request twice must not exchange the assignments
back or duplicate history.
